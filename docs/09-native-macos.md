## 1. Current product entry point

Olanzi's main application is a native macOS menu-bar app. It uses a complete SwiftUI interface for key configuration and AppKit for the menu-bar lifecycle, with device communication implemented in Swift through IOKit and CoreGraphics. Running the app requires no Python process, browser page, or local HTTP server.

The product remains a lightweight Studio alternative with room for additional device modules. Its initial scope is the AU05's three keys and three knob actions, background heartbeats, and host-side actions through the saved host map for ordinary keys and Fn, with optional double-press and long-press gestures, configurable app switching, and sequential macros. Additional firmware functions require their own protocol validation; the presence of a command in the reverse-engineered table does not make it safe to expose.

| Component | Role |
|---|---|
| `native/Package.swift` | Swift package; macOS 14 minimum, Swift 6 toolchain, Swift 5 language mode |
| `native/Sources/OlanziCore/` | TEA framing, IOKit transport, device state, CoreGraphics Fn events, dedicated background thread |
| `native/Sources/OlanziApp/` | SwiftUI keymap window, application state, AppKit menu bar |
| `native/Tests/` | Native core regression tests |
| `tools/build-macos.sh` | Builds and packages `build/Olanzi.app`; debug by default |
| Legacy Python and `web/` sources | Retained prototype and research tools; not the native app runtime |

## 2. Build and launch

Use macOS 14 or later with a Swift 6 toolchain. From the repository root:

```bash
make dev
```

`make dev` builds and opens the Debug app bundle at `build/Olanzi.app`. Launch the app bundle to use the native window and menu bar. No Python daemon command or browser URL is part of this startup path.

Other targets: `make build` builds Debug without launching, `make release` builds and signs Release and packages a DMG without launching, `make test` runs Swift tests, and `make check-docs` checks bilingual documentation. Both configurations share the `build/Olanzi.app` output path. If Olanzi is already running, quit it from the menu bar before running `make dev` to ensure the newly built version starts; `open` does not restart an existing process.

The build automatically uses the sole valid code-signing identity in your Keychain. If several exist, select one explicitly; if none exist, the build warns and falls back to ad-hoc signing. Set the same identity for Debug and Release to keep the signing requirement stable across rebuilds. A local self-signed certificate supports local development; it is not an Apple Developer distribution certificate or notarization.

```bash
make dev OLANZI_SIGNING_IDENTITY="Digger Local Signing"
```

The variable also accepts a certificate SHA-1 hash, or `-` to explicitly request ad-hoc signing. Signing uses the Keychain private key without exporting it. macOS may ask you to allow `codesign` to access that key.

To build the signed Release app and an installable disk image in one step:

```bash
make release
# Equivalent alias
make dmg
# Explicit signing identity
make release OLANZI_SIGNING_IDENTITY="Digger Local Signing"
```

The outputs are `build/Olanzi.app` and `build/Olanzi-<version>-<arch>.dmg` (currently `Olanzi-0.1.0-arm64.dmg` on Apple Silicon). The architecture comes from the compiled executable; this does not create a universal binary. The DMG contains the app and an Applications shortcut. Open it, drag Olanzi into Applications, then launch that installed copy. Quit a running copy before replacing it.

`tools/package-dmg.sh` packages the existing bundle; normally use `make release` so it is rebuilt first. Packaging signs the DMG with the app's certificate, checks the image checksum, mounts it read-only, verifies the bundled signature and file contents, checks the Applications link, and unmounts it before publishing the output. Temporary files are cleaned up; if unmounting fails, they are retained for recovery. No private key is exported. Local certificate signing is not Apple notarization.

For isolated UI development without real hardware:

```bash
swift run --package-path native Olanzi --demo
```

Demo mode must remain visibly distinguishable from a real device session. It uses simulated device behavior and does not open real HID interfaces or inject system Fn events. A successful demo preview is not evidence of real-device writes or OS actions.

Before connecting real hardware, quit official Studio and stop any legacy tool that still holds the device. The native app does not kill those processes on your behalf. Plug in the receiver, turn on Vibe Key, and check the app's connection state; receiver presence and device-online status are different observations.

## 3. Window and menu-bar lifecycle

Click the menu-bar icon to open a compact status panel showing receiver/device state, battery, keepalive, and permission or connection errors. It also provides connection controls, Resume Keepalive when paused, a single Settings button that always opens the main Keys page, and Quit.

The panel is constrained to the status icon’s screen, below the menu bar and notch safe area with a 4-point gap. Its position is checked again when its window moves or resizes.

The panel shows today's physical key presses (including knob press), knob turns, and active time, plus a seven-day active-time chart. Each device action starts a 30-second activity window; overlapping windows count once, only elapsed time is counted, and disconnect, sleep, or shutdown ends the window. This is an estimate of device activity, not Mac screen time or speech-input duration. Only events observed through the running driver's vendor channel count; historical activity before this feature or while the driver is stopped is unavailable. Missing days show zero.

Daily totals are stored locally for up to 30 days; no typed content or audio is recorded. Demo mode does not read or write real usage history. Storage failures appear in the panel without interrupting input forwarding.

The red close button and `Cmd-W` only hide the configuration window and retain drafts. Olanzi keeps running in the menu bar, and its Dock icon hides until the window is reopened. Its background device worker continues the connection, heartbeat scheduling, and ordinary-key and Fn forwarding through the saved host action map while the device is available and keepalive is not paused. Reopen the configuration window from the menu bar when you need to edit mappings. While a receiver is connected, the background worker holds an activity assertion against App Nap so hiding the window does not reduce heartbeat and input scheduling. It releases the assertion on disconnect or quit, and demo mode never acquires one. This assertion allows the Mac to sleep normally.

The main window has two navigation tabs: **Keys** and **Settings**. Settings combines the language selector at the top with Vibe Key status, keepalive, connection help, and keymap profile management below. Connection help stays visible under a question-mark-in-a-circle heading and cannot be collapsed. Open Settings from the top navigation or the macOS application menu (`Cmd-,`). Use its language selector to change the interface language. Options are Follow System (the default), English, and Simplified Chinese; unsupported system languages fall back to English. The selected preference is saved and takes effect immediately without restarting the app. Changing language preserves key mappings and unsaved drafts. User-defined profile names and file paths are not translated. The permission welcome page provides the same language selector, so language can be changed before granting permissions while the rest of the workspace remains gated.

Choose Quit from the application menu, or use the red power button at the bottom left of Settings, to stop the app and device worker. Shutdown attempts to release any synthetic Fn hold and closes the device interfaces. Closing a window is therefore different from quitting the app. Computer sleep interrupts continued heartbeat delivery regardless of whether the window is open.

No login item, `launchd` service, or automatic startup at boot is installed. Start the app manually when needed. Its menu-bar presence provides the background lifetime; a separate Python daemon is unnecessary.

## 4. Host actions and heartbeat

1. Load the existing host configuration first. If its file is missing, the app provides a factory-key draft without reading device mappings as its source or writing a file automatically. Once permissions are ready, this draft is editable even without a connected device. Existing device actions do not block editing. A corrupt local file is preserved and requires repair followed by an app restart.
2. Select an action around the centered device illustration. Prominent left/right arrows beside the knob each edit one rotation action. Each of the three keys has its own separated card on the right; knob press has a card on the left. Each card shows primary, double-press, and long-press labels above their assigned actions. Click an action to edit that control and gesture directly.
3. Review the selected action. Leaving optional double/long gestures unset preserves immediate primary-key response.
4. Apply to this Mac. The worker validates and atomically saves the complete map before activating it. This operation does not write device keycodes.

Selecting a keyboard action exposes its output options independently of the selected gesture. **Tap Once** sends one pulse and **Repeat** sends 2–20 pulses, defaulting to 2, with a separate setting for primary, double press, and long press. The repeat count appears only in Repeat mode. Primary and long-press actions also offer **Hold**: a primary-only action follows physical press/release, while a long action begins at its threshold and ends on release. With optional gestures configured, a primary waits for recognition; its Hold mode then emits one pulse. Double press is recognized on release, and rotary ticks have no release edge, so both offer only Tap Once and Repeat. These options can be clicked directly in the main window and do not apply to app switches, macros, or MO. Choosing a gesture and choosing an output count are separate edits.

Each repeat holds the action for 40 ms and leaves an 80 ms gap after release before the next press. The worker advances the schedule without blocking; a delayed worker extends these intervals rather than catching up with rapid pulses. Physical release does not cancel a triggered group, and continuing to hold does not restart it. Quick independent triggers use bounded pending execution. Disconnect, sleep, permission loss, or configuration replacement cancels pending groups and remaining pulses and releases active actions. Existing long-press modes and counts keep their behavior. New primary settings default to Hold and a repeat count of 2; double press defaults to Tap Once and a count of 2. Modes and counts remain draft edits until saved to this Mac. Physical primary, double-press, and rotary repeat output still requires verification.

The top-level Keymap, Device, Profiles, and Settings navigation remains in place. On Keymap, select the control and gesture in the upper device area, then use the lower key picker. Its left navigation includes Common, Characters, Function Keys, Numpad, Combinations, Layer, Apps, and Macros. Common includes navigation and modifier keys; Characters includes letters, digits, and symbols. The right area displays assignable keycaps, and search covers all keys. Buttons use the shared dark rounded theme with visible hover, disabled, and primary-action states. App and macro editing stays inside this lower area. The device area scales with the window, and the key picker fills the remaining height; keycaps flow to the available width, with scrolling when needed. Gesture cards display macro slot identifiers such as M0, while full names remain in the library and tooltips. Knob guide lines point toward the knob center, with mirrored spacing and gaps at both ends.

In Apps, choose **Add App**, select a local `.app`, and save the named library item. Click its A0, A1, or later keycap to assign it to the selected gesture. In Macros, choose **New Macro**, enter its name, and create 1–32 ordered steps combining app switches, keyboard combinations, and waits of 0.05–10 seconds. Add or delete steps and move them up or down. Save it to the draft library, then assign its M0, M1, or later keycap. Use the edit icon on a library card to edit that item. References are shared: editing one item updates every gesture using it after the page’s **Save to This Mac** succeeds. A referenced item cannot be deleted until those gesture bindings are removed or replaced.

The macro editor offers continuous keyboard recording, **Visual**, and **Code** views. Continuous recording adds successive combinations to the macro; the interval option controls whether waits are recorded between combinations. App switches remain available as manually added steps and can be freely combined with recorded keys and waits. Visual changes generate code; code must parse successfully before returning to Visual or saving the library item. Parse or validation errors preserve the typed text and previous steps. Saving the item updates the draft library; only **Save to This Mac** in the page footer activates the complete draft.

To record a sequence, start continuous recording in the macro editor, press and fully release each desired combination, then stop recording. With interval recording enabled, waits measure the time from one combination’s final release to the next combination’s first press, rounded to milliseconds. Gaps below 50 ms are omitted; a gap above 10 seconds stops recording and preserves completed steps. Keyboard and delay steps share the 32-step limit. Stopping or losing window focus discards an unfinished combination and retains completed steps for review. Esc, Enter, and Command-Q are recording inputs too; click the stop button to finish. Recording captures keyboard input only; add app switches manually afterward.

For Codex, choose **Fill Codex Focus Macro** in the macro editor to add an app switch to `com.openai.codex`, a 0.8-second wait, and `⌃⌥⌘I`. Save the named macro to the draft library, assign its M keycap to the desired gesture, and save to this Mac. This uses the shortcut from the earlier Raycast script directly. At execution time, the driver launches target apps if needed and waits for foreground confirmation. App switches and macros run once after gesture recognition; keeping a long press held does not repeat them. Activation failure or loss of the selected foreground app stops subsequent macro keys. Disconnect, sleep, permission loss, configuration replacement, and quitting cancel pending execution.

Code accepts a subset of the [QMK macro syntax](https://docs.qmk.fm/feature_macros) and supported [QMK keycodes](https://docs.qmk.fm/keycodes), not complete C source or firmware. Use a sequence of statements, such as this Codex workflow:

```c
OLANZI_APP("com.openai.codex");
wait_ms(800);
tap_code16(LCTL(LALT(LGUI(KC_I))));
```

`OLANZI_APP` is an Olanzi extension, not a QMK function. It accepts either a bundle identifier alone or exactly three arguments: bundle identifier, app path, and display name; the bundle-only example resolves a locally installed app. `OLANZI_FN` is the Olanzi key constant for Mac Fn. These extensions run through the host driver and do not modify firmware.

| Supported code | Meaning and limits |
|---|---|
| `tap_code(KC_A);` | Emit one supported basic key pulse. |
| `tap_code16(LCTL(LALT(LGUI(KC_I))));` | Emit a key with nested Control, Shift, Alt/Option, or GUI/Command modifiers. Left- and right-side modifiers cannot be mixed in one `tap_code16` expression. |
| `wait_ms(800);` | Wait an integer 50–10000 milliseconds. |
| `SEND_STRING("Hi");` | Expand supported ASCII using US ANSI key positions; this is not Unicode text injection and output depends on the active keyboard layout. |
| `SEND_STRING(SS_TAP(X_I) SS_DELAY(800));` | Expand supported key taps and waits. Modifier wrappers such as `SS_LCTL(...)` apply to one key with no enclosed delay. |
| `register_code(KC_A); register_code(KC_B); unregister_code(KC_B); unregister_code(KC_A);` | Represent a simultaneous multi-key combination. Presses must form one group, followed by releases in reverse order, without intervening waits or interleaved actions. |

Unknown or unsupported syntax reports a line and column and is not executed. The editor accepts at most 32 KiB of code and 32 levels of nesting, and the expanded result must still fit the 1–32 macro-step limit. Converting between views preserves executable steps, not the original whitespace, comments, or choice of equivalent syntax.

The device illustration and action cards are the control selector; there is no repeated control list. The key picker always includes **▽** and a **rounded square with a cross (`xmark.square`)** (No Action) instead of separate clear-action and restore-inheritance buttons. On a non-base layer, ▽ restores only the selected gesture’s lower-layer action, output mode, and repeat count, preserving other overrides; Layer 0 cannot inherit. The crossed-square keycap makes a primary action an explicit no-op, or disables the selected double/long gesture so it no longer participates in recognition, including when a lower layer has that gesture. Inherited actions display a downward triangle with explanatory hover and accessibility text. Timing and Fn explanations are in the question-mark help. The footer shows pending changes or a save in progress, without a routine saved-state label; errors remain visible. Settings keeps connection help permanently visible with a question-mark-in-a-circle heading and omits heartbeat counters.

Operation feedback, including saves, appears as a floating capsule near the top of the window. Its `Capsule` shape has semicircular ends and occupies no page-layout space. Short messages dismiss after about 3.5 seconds, longer ones after 7 seconds, and either can be closed manually; repeating the same notice restarts its timer.

To assign a key combination, select a control and gesture in the upper device area, choose **Combinations** in the lower category list, and click **Record Shortcut**. Hold the keys together, such as A+B or Control+A+B, then release every key to finish and preview the combination. Modifier-only combinations and Fn can also be recorded; select Caps Lock from the regular key categories. Left and right modifiers are normalized to their left-side forms. Record Shortcut starts a fresh attempt; Cancel Recording discards the current recording. **Assign Shortcut** puts the result into the selected gesture draft; save it to this Mac to activate it. Switching controls, gestures, or categories stops capture, as does leaving the app. These combinations hold keys together; they are not timed macros. macOS may intercept system shortcuts before they reach the recorder.

The host map is authoritative for all six controls while Olanzi is forwarding with keepalive active, including ordinary keys and Fn. An existing map or a new default draft can be edited offline; a new draft becomes active only after an explicit successful save. Device refresh and reconnection do not overwrite it. Saved and exported version-2 `HostProfile` JSON includes primary, double-press, and long-press actions, the keyboard output modes and repeat counts for each gesture, timing values, app targets, named library items and their shared references, and complete macro steps. Double/long gestures remain supported; moving the complete configuration between Macs uses export on one Mac and import followed by an explicit local save on the other. Automatic cross-Mac synchronization through the device is not provided. Old six-key native profiles migrate into primary actions. See [10 · Daemon Input Runtime](10-input-runtime.md) for ownership, timing, and migration details.

Exports default to `vibe-key-yyyy-MM-dd_HH-mm-ss-SSS.json`, using the current local date and time down to milliseconds to distinguish successive exports.

The Key Profiles section in Settings offers `从设备键位导入` (import device mappings) as an optional action. It validates the six-control read-only snapshot before loading a draft. An unsupported action identifies the affected control and leaves the current draft unchanged. Importing does not save or activate the draft. The on-device key table remains an independent fallback. Explicit hardware writes through the protocol tool still require ACK/readback and can partially succeed; the native host-action editor no longer invokes that operation. Drafts are separate from both the saved host map and hardware snapshot.

The heartbeat follows Studio's recovered plaintext prefix `06 01 23 00 01` with zero padding. Because it selects vendor-event forwarding, it is enabled only with a successfully saved valid host map, a connected and online device, Input Monitoring and Accessibility permissions, and unsuspended input. Otherwise heartbeats stop while read-only online and key queries remain available; query waits also check permissions and sleep state. Successful transmission does not alone prove radio delivery or idle wakefulness. See [07 · Heartbeat Investigation](07-heartbeat-investigation.md).

The Vibe Key section in Settings provides an idle-stop preference: **Never** (default), or **1, 5, 10, 15, 30, or 60 minutes**. Changes save immediately on this Mac, separately from keymap drafts and profiles. Only physical Vibe Key key and knob actions count as activity. Holding a push control prevents timeout; releasing it starts a new idle interval. Status and battery queries, other computer input, and hiding the window do not reset that interval.

At timeout, the worker stops heartbeats, cancels host gestures, momentary layers, keyboard repeats, and macros, and releases owned keys. The device may return to its firmware mappings. Physical activity while paused requests automatic resumption after all controls are released and trailing reports drain for 100 ms. The wake gesture is not replayed, avoiding duplicate output if standard HID has resumed. Use **Resume Keepalive** in Settings or in the menu bar to resume. A real receiver reconnection, Mac wake, or confirmed device offline-to-online transition also starts a new interval; recovery from an unknown status after a failed query does not clear the pause. Device sleep timing and power savings still require physical verification.

An idle pause also stops the background online query every two seconds and battery query every 20 seconds, retaining receive callbacks and USB removal detection so background traffic does not interfere with firmware standby and sleep timers. Online status and battery values remain the last readings before the pause, not proof of current wakefulness. While paused, the service also passively listens to AU05 standard HID interfaces without sending queries; both vendor events and standard HID activity can request automatic resumption. Other computer keyboards cannot trigger it. Missing monitoring permissions or interface failures are reported; **Resume Keepalive** remains available. Explicit connection checks or refreshes still send requests, but a successful query alone does not clear the pause. Stopping keepalive does not change on-device standby or sleep durations or imply immediate sleep; actual timing and power savings require hardware verification.

Idle pause follows the VibeKey Lite host-control handoff: after stopping heartbeats, synchronously send `01 01 10 00 00` (software offline); when resuming, send `01 01 10 00 03` (software online) successfully before allowing heartbeats. All writes run serially on the device worker, outside HID callbacks. Disconnect, quit, and Mac sleep also attempt to return control; a failed handoff reports an error and stops host control until Resume Keepalive retries it. This flow does not change stored lighting, standby, or sleep settings. Knob-light shutoff and actual sleep timing still require hardware verification.

The main window displays battery status below the connection state at the top right. While the device is online and not paused for inactivity, the worker sends the read-only `01 01 02 01` query every 20 seconds and records the latest successful timestamp. The UI shows percentage and charging status, with levels at or below 20% in orange. Offline, unknown, or failed readings show `电量 —`; if only percentage is unavailable, a valid voltage is shown instead. The tooltip gives voltage, update time, or an independent read error. Battery failures clear the stale reading and retry on the next interval without disabling Fn forwarding. Decoding is based on [02 · Protocol](02-vibekey-protocol.md#battery-reply-fields); the current sample and verification boundary are in [05 §9.10](05-verification-log.md#910-read-only-battery-status-and-main-window-display).

## 5. Vendor Key Forwarding, Fn, and Permissions

[CONFIRMED] The physical comparison on 2026-09-21 found that one-second Studio heartbeats from Olanzi stopped ordinary-key standard HID output and left the Fn standard-input callback without reports. Closing only the Fn input interface did not help; stopping only the heartbeat while retaining the vendor connection and read-only queries restored Enter. Keys then appeared as `8b 10` vendor events; see [07 §4](07-heartbeat-investigation.md). Both ordinary keys and Fn therefore require application-side forwarding and its permissions.

`GestureRouter` interprets the event's physical control index using the saved host map; `VendorKeyBridge` executes the selected keyboard action, app switch, or macro. The logical action number in `frame[2]` is not a HID keycode and must not be injected directly; the AU05 physical index is in `frame[4]`. Unapplied drafts do not participate in forwarding. Unknown or multimedia mappings must produce explicit errors rather than guessed input. Physical capture has confirmed all six control indices and rotation directions; rotation indices 4/5 report only down, requiring a host-supplied release pulse. The preceding vendor-routing implementation passed 68 automated tests and a signed Release build; the host-runtime checks are described in [10](10-input-runtime.md). That earlier build confirmed physical Enter and top-key Fn effects. A later knob-to-F13 test confirmed the earlier Raycast script’s input-field focus action; see [10 §4](10-input-runtime.md#4-holds-cancellation-and-failures). These results do not establish every control or application action, or the new direct Codex macro.

Fn remains an ordinary key name in Common: select it and apply, without a separate feature switch or `macFnEnabled` setting. Device keycode `0x01` means Fn in the host mapping; the factory top key also uses it. Vendor events carry physical control indices, so the old standard-HID prototype's inability to distinguish same-code controls does not directly apply. Removing every Fn assignment stops Fn generation, while ordinary-key forwarding still requires the bridge and permissions.

Give **Olanzi App** both Input Monitoring and Accessibility permission in System Settings → Privacy & Security. These permissions belong to the native bundle, not the legacy terminal process. Outside demo mode, either missing permission shows only a permission welcome page inside the main app window by replacing its content, without opening a popup, another window, a sheet, the configuration workspace, or the settings interface or stacking initialization errors and a footer error bar. The welcome page provides separate Input Monitoring and Accessibility guidance, buttons for the corresponding system settings, and an app-location entry point. This guidance is independent of map initialization and device online status. Both permissions becoming ready automatically opens the workspace; revocation returns to the welcome page. Demo mode bypasses this gate. Automated regression, build, and real-UI verification of the welcome-page gate passed: one Olanzi main window showed the welcome text, both permission states, and settings and app-location controls, without configuration navigation, initialization errors, a save footer, or an additional popup. Clicking requests the selected permission directly on the app main thread before opening the matching System Settings page; the request no longer waits for the device worker or connection. Input Monitoring uses the HID request API, with an event-listening request as a fallback if access remains denied. The app requests one permission at a time, without adding a separate Fn panel. System policy and existing denial records can still prevent a new prompt; opening Settings alone is not evidence that the app was registered. The app checks permissions once per second without prompting, independently of window activation and the device worker. The UI stores these results separately so older device snapshots cannot overwrite newer permission state; changes automatically switch between the welcome page and workspace and ask the device service to recheck. Stopping the app cancels the timer, and demo mode does not poll. If Settings is enabled but the running process still reports unavailable access, first verify the authorized app copy and path; a Settings switch alone does not establish current-process permission. Ordinary-key and Fn forwarding both depend on these permissions; a device mapping does not establish that access is ready or forwarding is active.

If Olanzi is absent from the settings list, click + to add it. The “Show App Location” button on the welcome page or in Settings → Connection Help reveals the running bundle in Finder. Grant permission to that copy at a stable path, such as the repository's `build/Olanzi.app` or `~/Applications/Olanzi.app`. Reuse the same signing certificate and bundle identifier across builds. Switching from ad-hoc signing to a certificate changes the signing requirement, so existing permissions may need to be removed and granted again once. Stable signing does not grant permissions automatically. [CONFIRMED] `codesign` verification of this local build identified the sole Apple Development identity in the keychain and bundle identifier `com.mrcroxx.olanzi`, with no ad-hoc signing. Missing permissions still require user approval in System Settings.

Input Monitoring first reads `CGPreflightListenEventAccess()`. If it is false, a temporary session-level, listen-only event tap containing only key-down/key-up events checks the current process's keyboard-listening capability. The probe must be both valid and enabled and is immediately invalidated and released, without joining a run loop or collecting keyboard content. `IOHIDCheckAccess()` and event-synthesis preflight remain diagnostic values. Accessibility independently reads `AXIsProcessTrusted()` on every check, without short-circuiting on other preflights. Diagnostics include `ListenProbe`, distinguishing probe results from skipped checks. The UI reports current listening capability as `已就绪` (ready), not the separate Settings switch, and does not establish any permission API's caching mechanism. It supersedes the preflight-only decision and conditional AX checks from §9.5/§9.6; see [05 §9.7](05-verification-log.md#97-checking-keyboard-listening-capability-after-a-negative-preflight) for in-process evidence and verification limits.

If migrating from an older ad-hoc build leaves stale denial records, quit Olanzi, reset only its affected permissions, then relaunch the installed copy and click its permission button. This removes existing approvals for those services, which must be granted again. The app never runs these reset commands automatically.

```bash
tccutil reset Accessibility com.mrcroxx.olanzi
tccutil reset PostEvent com.mrcroxx.olanzi
tccutil reset ListenEvent com.mrcroxx.olanzi
open /Applications/Olanzi.app
```


The new forwarding path consumes key events from the existing vendor connection instead of relying on the silent Fn standard-input callback. All key forwarding requires a running app, an online device, a valid saved host map, and the relevant permissions. Closing the window keeps it running; quitting stops it. The implementation must track holds by physical control, avoid duplicate presses, and attempt releases on key-up, disconnect, or quit; Enter and one top-key Fn press/release pair have earlier physical confirmation, which does not establish physical coverage of every control or failure-release scenario.

Fn conversion is not a native firmware Fn command, and neither the protocol nor a simulated event test proves equivalence to an Apple hardware Fn/Globe key. Dictation, input-source switching, Studio-specific Fn handling, and application-specific actions still require physical testing. See [08 · Mac Fn](08-mac-fn.md) for the trigger mechanism and historical prototype implementation; its Python commands and HTTP settings do not apply to the native app.

The native bridge posts Fn events at `cghidEventTap`, retaining a private event source and paired `flagsChanged` events. [CONFIRMED] Inspection of the running Doubao input method found its listener at the HID tap; Studio's general keyboard emitter also posts there. The previous session-level injection bypassed listeners at that earlier stage. Moving injection to the HID tap corrects the routing mismatch; an earlier physical test confirmed top-key Fn activation of Doubao and a cleared Fn bit on release, within the historical test below. That addresses only the injection-stage mismatch. The new heartbeat comparison additionally establishes a standard-HID-to-vendor-event transition, which a Fn tap change alone cannot fix. Ordinary-key and Fn forwarding still use a private CoreGraphics source and the HID tap. A private source does not isolate `.hidSystemState`: later in-process measurements found that both `flagsState` and `keyState` included the app’s synthetic Fn feedback. `PhysicalFnMonitor` now tracks physical Fn and left/right Control, Shift, Option, and Command through a session-level, listen-only `flagsChanged` tap. It accepts only source PID 0 and updates only the side identified by that event’s virtual keycode, avoiding synthetic feedback in unrelated flag bits. The cache starts empty without aggregate-state seeding; `VendorKeyBridge` prepares monitoring before forwarding and stops with an error if preparation fails. In the main path, `MacKeyEmitter` removes these modifiers’ family and side bits from aggregate flags, then merges the monitored state and app-owned holds. Other state, such as Caps Lock, retains its existing handling. The legacy native backend still uses the monitor’s Fn state. A disabled tap clears the untrusted cache before attempting re-enabling; it does not indefinitely pause forwarding while waiting for a physical key event. The next physical side-key event rebuilds that side’s state. Physical modifiers already held before startup or during a missed-event interval must be released and pressed again. The monitor reads modifier metadata only and releases its run-loop source and tap on destruction. Logs at 00:42:57/59 on 2026-09-22 observed one physical Fn press/release pair from PID 0, establishing that sample rather than every keyboard-overlap case; see the [modifier-feedback excerpt](evidence/2026-09-22-modifier-feedback.log). The earlier Fn-only revision is recorded in [05 §9.9](05-verification-log.md#99-synthetic-fn-feedback-contaminating-the-hid-state); the two post-fix physical trials and their limits are recorded below.

For a sustained Fn hold, assign Fn to the primary action, choose Hold, and disable optional gestures: it stays held until release. A long-press Fn action set to Hold begins holding after its threshold and ends on release; Tap Once emits a single Fn pulse at the threshold, while Repeat emits the configured number of Fn pulses; neither repeats a group merely because the control remains held. Primary Fn combined with other gestures, and double-press Fn, produce one or repeated pulses according to their output mode after gesture recognition; primary Hold becomes one pulse in this case; the UI explains this distinction. These are the runtime’s action semantics, not proof of an input method’s response.
