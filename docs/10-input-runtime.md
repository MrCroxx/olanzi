## 1. Ownership and scope

All six controls enter one host input pipeline. The menu-bar application's device worker owns the receiver, heartbeat, gesture clock, committed action map, and generated key holds. The window edits drafts and submits configurations; closing it does not stop the worker. This is an in-process background service, not a separately installed launch daemon or login item. Quitting the app stops forwarding.

The previous implementation looked up each event in the device's key table. That conflated the hardware fallback with runtime actions and had no place to recognize double presses or long presses. The runtime now loads the persistent host configuration first. A missing file makes the UI offer its own default draft; the worker does not seed from device mappings or write a file automatically. Device snapshots remain independent, and refreshes and reconnects do not replace the host configuration or draft. Normal edits never issue a hardware key-table write.

| Layer | Responsibility |
|---|---|
| `MacHIDTransport` | Decode vendor frames and deliver physical-control edges, including while a query is waiting |
| `GestureRouter` | Interpret edges and monotonic deadlines; choose exactly one configured action |
| `VendorKeyBridge` | Route selected actions, execute keyboard holds, preserve shared modifiers, and retry failed releases |
| `HostActionRunner` | Advance app activation and ordered macro steps without blocking the device worker |
| `MacKeyEmitter` | Translate keyboard usages to macOS events and post at the HID tap |
| `PhysicalFnMonitor` | Track physical Fn metadata independently of aggregate synthetic-event feedback |
| `HostKeymapStore` | Validate and atomically persist the authoritative host configuration |
| SwiftUI / `AppModel` | Edit drafts, choose gestures, import/export profiles, and submit saves |

Vendor events identify controls independently of their configured actions. The AU05 physical index is `frame[4]`; `frame[2]` is a logical action number and is never injected as a keyboard usage. The four push controls send press/release edges. Rotary controls 4 and 5 send a press-only pulse per tick. See [the routing capture](evidence/2026-09-21-vendor-key-routing.log).

## 2. Actions and timing

Each control has a primary `press` action. The four push controls may additionally configure `doublePress` and `longPress`. Each action selects keyboard entries, an app target, or an ordered macro. The keyboard picker assigns one key to the chosen action, while the compact recorder assigns combinations that can include multiple ordinary keys and modifiers. Keyboard long-press actions also have a `longPressBehavior`: `hold` (default) keeps the action down from its threshold until physical release, `tap` emits one down/up pulse, and `burst` emits a configured number of pulses after the threshold. The inline buttons, shown only when editing a keyboard long press, label these options Hold, Tap Once, and Repeat; only Repeat shows a count stepper, defaulting to 2 and bounded to 2–20. An absent optional action disables that gesture, while a configured unassigned key is an intentional no-op. Rotary controls reject double/long mappings. App switching and macros execute once per recognized gesture; their long-press execution does not use keyboard hold, tap, or burst behavior.

An app action identifies a local application selected through the `.app` picker. Execution launches it if needed, requests activation, and waits until it is confirmed as the foreground application before continuing. Macros contain 1–32 non-nested steps, each an app switch, a keyboard combination, or a wait of 0.05–10 seconds. Steps execute in their configured order; keyboard steps emit a pulse rather than remaining held for later steps. The editor can add, delete, and reorder steps. App actions and macros execute serially. A control can have at most one queued or running action, and the global queue plus running action is capped at eight; extra triggers are ignored. Keyboard macro steps hold keys for 40 ms, and app activation must complete with foreground confirmation within five seconds. Neither waits nor activation block heartbeat processing.

Open the Macros category in the lower key picker, create a named macro, and choose **Fill Codex Focus Macro**. The template fills the editor with an app switch to `com.openai.codex`, a 0.8-second wait, and `⌃⌥⌘I`. Save the library item, assign its M keycap to a gesture, and explicitly save the complete draft to this Mac. The wait can be adjusted for the target application; foreground confirmation does not prove that a specific input field is ready. The new direct workflow still requires physical and target-application verification.

The editor places distinct gesture cards around a centered device illustration: one card for each of the three keys on the right and one for knob press on the left. Each card has three columns with the gesture name above its action; clicking an action selects that control and gesture. Left/right rotation arrows flank the knob and each expose only a primary action. There is no duplicate control list. Detailed timing and Fn explanations are available through question-mark help; normal operation omits saved-state labels and heartbeat counters while keeping errors visible.

| Configuration or event | Behavior |
|---|---|
| No optional gesture | Keyboard primary down is immediate; primary up follows physical release. Fn and modifiers acquire no gesture delay. Other action types start once immediately. |
| Long press only | Release before the threshold emits one primary pulse; reaching the threshold executes a keyboard long action using Hold, Tap Once, or Repeat, or starts an app switch or macro once. |
| Double press configured | The first release waits for the double-press window; expiry emits one primary pulse. |
| Second down before the double deadline | Claims the second press; its release emits one double action pulse. |
| Second press reaches the long threshold | A configured long action takes precedence; neither the pending primary nor double action is emitted. |
| Second down exactly at or after the deadline | The first primary expires first; the new down starts another gesture. |
| Rotary tick | Execute the primary action once immediately; keyboard actions receive a down/up pair without waiting for a device release. |

Repeat schedules each action down for 40 ms, then leaves an 80 ms gap from up to the next down. It starts only once after the long-press threshold; releasing the physical control after it starts does not cancel the remaining group, and continuing to hold does not start another group. A delayed worker advances one edge at a time and schedules the next deadline from the actual advancement time, rather than catching up with overdue pulses. Disconnect, sleep, permission loss, configuration replacement, or an execution error cancels the remainder and attempts to release active keys.

The default double-press window is 250 ms from the first release; the long-press threshold is 500 ms from the relevant press. Configuration accepts a double window of 150–500 ms and a long threshold of 300–2000 ms, with the long threshold greater than the double window. The clock is monotonic. Duplicate down packets do not restart a hold or deadline.

Enabling an optional gesture necessarily delays the ambiguous primary action. Keep optional gestures disabled on a control that must immediately act as a held Fn, Shift, or other modifier. A long action mapped to Fn with Hold begins holding Fn only after its threshold and releases when the control is released; Tap Once emits one Fn pulse at the threshold, while Repeat emits the configured number of pulses; continuing to hold does not repeat either group. Primary Fn with another gesture enabled, and double-press Fn, are pulses after gesture recognition. The UI explains continuous holds versus pulses; an input method’s actual behavior still requires physical verification.

## 3. Configuration and migration

The active map is stored at `~/Library/Application Support/Olanzi/host-keymap.json`. It contains six unique control indices, the action entries, timing values, and schema version. The store validates before writing, uses an atomic replacement, and does not activate a new map when persistence fails. If the file is missing, the worker publishes `hostConfigurationMissing=true` without creating a map or writing a file. The app offers `HostKeymap.defaultKeymap` as an editable draft, independent of device presence or the types in its old key table. A corrupt or unsupported local file remains an error, requires repair followed by an app restart, and cannot be overwritten by a draft. Only an explicit successful save persists and activates a new host map; until then, the default draft does not enable heartbeats. This process never writes the device key table.

The device table is a separate fallback used when the app is absent and the receiver returns to standard HID output. Editing the fallback remains an explicit protocol-tool operation described in [03 · Tool Manual](03-tool-manual.md). Applying a host map or importing a profile does not rewrite it. The profile page can explicitly import the read-only device key snapshot into a draft. All six controls must validate; a failure identifies the affected control and preserves the existing draft. This optional import is not initialization or activation. Default drafts and existing host maps can be edited and saved offline; demo mode uses memory only and never touches the real host store or device.

Exported `HostProfile` version 2 includes every control’s `press`, optional `doublePress` and `longPress` actions, the `longPressBehavior` value (`hold`, `tap`, or `burst`), the `longPressTapCount` repeat count, and the `doublePressWindow` and `longPressThreshold` timing values, together with app targets and complete macro steps. Existing keyboard-only actions remain compatible. The outer profile stays at version 2. Its nested `HostKeymap` writes version 3 when an action library or library reference is present. The reader accepts map versions 1, 2, and 3, preserving older keyboard mappings and inline app/macro actions. Without a library or references, serialization uses version 2 for extended actions or version 1 for keyboard-only mappings. Older profiles without `longPressBehavior` decode as `hold`, and a missing `longPressTapCount` defaults to 2. Existing Hold and Tap Once profiles retain their behavior; the count is validated within 2–20 in every mode. Rotary controls do not support long-press behavior. Double/long gestures remain supported. The chosen cross-Mac workflow is to export this complete JSON, import it on the destination Mac, and explicitly save it locally. Automatic cross-Mac synchronization through the device is not provided, and profile transfer never writes the device key table. Import accepts legacy native version-1 six-code profiles by turning their codes into primary actions with optional gestures disabled. Saved profile collections use `nativeHostProfiles`; the old `nativeProfiles` collection remains available as the migration source. Entries are decoded and migrated independently, so one corrupt or unsupported entry cannot prevent valid profiles from loading. Complete original data containing failed entries is backed up in `nativeHostProfilesRecoveryBackups`; subsequent profile saves or deletions do not overwrite that recovery copy. Import is bounded to 32 KiB and rejects invalid versions, duplicate/missing controls, unsupported keys, invalid timings, and rotary gesture mappings.

Version 3 adds `actionLibrary`, whose `NamedHostAction` entries have a stable UUID `id`, a 1–80-character `name`, a numeric `slot`, and an app or macro `action`. Apps use A0–A15 and macros M0–M15; slot allocation is independent for each category. Control actions reference an item by its UUID, and the runtime resolves the reference against the committed map. Library items cannot reference other library items or contain standalone keyboard actions. Validation rejects missing references, duplicate IDs or same-category slots, and invalid names or actions. Unassigned items are saved and exported too. Editing an item preserves its identity and updates all references after local save; deleting a referenced item is rejected until all its bindings are removed. Library edits, assignments, and deletions share the same draft and atomic-save boundary.

The lower picker’s Combinations category records a simultaneous group through the same host-map workflow, including A+B, Control+A+B, modifier-only combinations, and Fn. Releasing all keys finishes the group and displays its preview. This single-combination recorder does not save macro timing; continuous recording in the macro editor uses `MacroRecordingSession` to collect successive completed groups and optional gaps. Left and right modifiers are normalized to their left-side forms; Caps Lock remains selectable through the regular key categories. **Assign Shortcut** replaces the selected gesture draft, and the map becomes persistent and active only after explicit local save succeeds. Switching the selected control, gesture, or category, or leaving the app, stops capture. System-reserved shortcuts may not reach the recorder. See [09 §4](09-native-macos.md#4-host-actions-and-heartbeat) for the recording steps.

Macro Code is an editor representation of the same `[MacroStep]` values used by Visual mode. `QMKMacroCodec` parses only its supported QMK statement subset; it does not compile C, run arbitrary functions, or interpret firmware state. App switching and Mac Fn use explicit Olanzi extensions. Parsing and step validation finish before replacing the editor sequence, so invalid code leaves both the input text and prior actions intact. Successful conversion does not activate the map: saving the library item updates the draft, and the page footer’s local save remains the persistence boundary. Code text, comments, and formatting are not a second stored macro format. Supported syntax and the Codex example are documented in [09 §4](09-native-macos.md#4-host-actions-and-heartbeat).

The interface-language preference is independent of the host map and exported profiles. Follow System defaults to English when the system language is unsupported; English and Simplified Chinese can also be selected explicitly. Switching language updates the interface immediately and saves the preference without replacing the active map, discarding draft actions, or translating user-defined profile names and file paths. See [09 · Native macOS App](09-native-macos.md#3-window-and-menu-bar-lifecycle) for the Settings and permission-welcome-page entry points.

Each save has a distinct request ID and returns its matching success or failure in the snapshot. The UI ends its pending-save state only for that request, rather than treating busy-state changes from refresh or reconnection as save completion. Further draft edits made during the save remain intact.

## 4. Holds, cancellation, and failures

An emitted hold owns a snapshot of its action. Shared macOS keys are reference-counted across controls, including aliases such as Print Screen and F13; releasing one control must not release another control's key. Other active modifiers remain present in emitted flags. Every rotary tick receives a host-generated release.

[CONFIRMED] F1–F20 down and up events also carry their own function flag. This shares a bit with physical Fn but does not represent an additional Fn hold. See Apple's [function flag documentation](https://developer.apple.com/documentation/appkit/nsevent/modifierflags-swift.struct/function). Investigation of an F13 hotkey on 2026-09-22 found that the old emitter omitted this bit when overwriting event flags; two new regression tests failed before the fix. The emitter now adds it by macOS virtual key, including Print Screen and other F13–F15 aliases, without registering them as held modifiers. Subsequent ordinary keys and Fn releases still clear synthetic feedback. All 173 tests passed after the fix, and the build was signed with the existing Keychain identity. Physical logs captured F13 events corresponding to knob presses and releases, alongside successful Raycast script runs at matching times. The user confirmed that both attempts focused the input field. This verifies the current script and configuration, not every application hotkey. See the [raw F13 verification log](evidence/2026-09-22-f13-hotkey.log).

`PhysicalFnMonitor` now tracks physical Fn and both sides of Control, Shift, Option, and Command through a session-level, listen-only `flagsChanged` tap. It accepts source PID 0 and updates only the side identified by the event’s virtual keycode, without inheriting unrelated flag bits or seeding from aggregate system state. The cache starts empty. `VendorKeyBridge` prepares monitoring before forwarding; preparation failure disables forwarding with an error. The legacy `NativeFnBackend.open` also starts the monitor before event emission and uses its Fn state. In the main emitter, these modifiers’ family and side bits are removed from aggregate flags before merging the monitored state and app-owned holds; Caps Lock and other state retain their existing handling. When the tap is disabled, its untrusted cache is cleared before re-enabling. Forwarding does not wait indefinitely for physical key input; the next side-key event rebuilds that side’s state. A physical modifier already held at startup or during a missed-event interval must be released and pressed again. Invalid ports and failed creation or re-enabling report errors; destruction removes and releases the run-loop source and tap. The monitor reads modifier metadata, not keyboard text. The log at 00:42:57/59 on 2026-09-22 observes one physical Fn press/release pair from source PID 0, not every keyboard-overlap case; see the [modifier-feedback excerpt](evidence/2026-09-22-modifier-feedback.log). The two post-fix physical trials and their limits are recorded below.

Disconnect, loss of online status or permissions, system sleep, configuration replacement, and shutdown cancel unresolved gestures and any remaining repeat pulses or macro steps, and attempt to release owned keys. Cancellation never flushes a delayed single action into the newly focused application. Held push controls are quarantined until their physical release after a configuration change, preventing a held key from becoming a new action under the replacement map. A failed release remains pending for retry rather than being treated as successful. Sleep immediately gates input callbacks while the worker cancels gestures and closes the connection; waking reconnects only if the user had not manually disconnected. No pending pre-sleep action is replayed.

An app activation error or timeout stops the remaining macro. After a macro selects an app, subsequent key steps require that app to remain in the foreground; a focus change cancels the sequence rather than sending those keys into a different app. Cancellation invalidates pending activation work so late completions cannot resume a canceled macro. A target app may still finish launching after cancellation, but its remaining macro keys are not replayed.

Studio heartbeats default to disabled. They are enabled only when a successfully saved valid host map, a connected and online device, Input Monitoring and Accessibility permissions, and unsuspended input are all ready. An unsaved default draft, a local configuration-file error, or missing permissions leaves read-only vendor queries available without continuing to take over device input through heartbeats. Permission diagnostics are independent of map initialization and device online status. Outside demo mode, missing Input Monitoring or Accessibility permission replaces the main app window's content with the permission welcome page and authorization guidance, without opening a popup, another window, or a sheet, or entering the configuration workspace or settings interface. Both permissions becoming ready opens the workspace automatically; revocation returns to the welcome page, without stacking initialization errors and footer notices. Query waits also check suspension conditions. Normal online queries retain the last confirmed state until completion, avoiding cancellation of held actions every two seconds.

The app independently reads `InputPermission.currentStatus()` once per second in the main run loop's common mode, without depending on window activation or completion of device jobs and without requesting authorization. Polled results are stored separately so older device snapshots cannot roll them back; only changes ask the service to recheck immediately and automatically switch the welcome page. Stopping or destroying the model cancels the timer; demo mode does not read real permissions. Input Monitoring first reads the CG listening preflight. Only when false does it create a temporary session-level, listen-only, keyboard-only capability probe, checking that it is valid and enabled before immediately releasing it without joining a run loop or reading events. A true preflight skips the probe. Either successful check means current keyboard-listening capability is `已就绪` (ready), not that the UI mirrors a separate Settings switch. HID and event-synthesis preflight remain diagnostic values. Accessibility reads `AXIsProcessTrusted()` unconditionally on every check, preventing any other preflight from short-circuiting the real AX state. `ListenProbe` diagnostics distinguish probe results from skipped checks.

Device-query waits continue to deliver physical events, so a readback cannot compress an entire Fn hold into two events after the query returns. Gesture deadlines are serviced by the worker; no window timer owns input behavior. Explicit device-map import, profile import, and host-action validation reject unknown action types and unsupported macOS usages instead of guessing input. Unsupported types in an ordinary device readback do not block default drafts or an existing host map. F21–F24 have no supported virtual-key mapping in this implementation.
