## 1. 当前产品入口

Olanzi 的主应用是原生 macOS 菜单栏 App。键位配置使用完整 SwiftUI 界面，菜单栏生命周期由 AppKit 管理，设备通信通过 Swift 直接调用 IOKit 与 CoreGraphics。运行 App 不需要 Python 进程、浏览器页面或本地 HTTP 服务。

产品仍定位为可扩展设备模块的轻量 Studio 替代客户端。首期范围是 AU05 的三个按键和三个旋钮动作、后台心跳，以及按已保存本机映射执行的普通键与 Fn 主机转发，支持可选双击和长按手势、可配置的切换 APP 与顺序宏。其他固件功能需要独立验证协议；逆向命令表里存在命令，并不意味着可以安全开放。

| 组件 | 职责 |
|---|---|
| `native/Package.swift` | Swift 包；最低 macOS 14、Swift 6 工具链、Swift 5 语言模式 |
| `native/Sources/OlanziCore/` | TEA 帧处理、IOKit 传输、设备状态、CoreGraphics Fn 事件、专用后台线程 |
| `native/Sources/OlanziApp/` | SwiftUI 键位窗口、应用状态、AppKit 菜单栏 |
| `native/Tests/` | 原生核心回归测试 |
| `tools/build-macos.sh` | 构建打包 `build/Olanzi.app`，默认 debug |
| 旧 Python 与 `web/` 源码 | 保留的原型与研究工具，不是原生 App 的运行时 |

## 2. 构建与启动

使用 macOS 14 或更新版本，以及 Swift 6 工具链。从仓库根目录运行：

```bash
make dev
```

`make dev` 编译并打开 `build/Olanzi.app` 下的 Debug 应用包。打开应用包即可使用原生窗口与菜单栏；这条启动路径不包含 Python daemon 命令或浏览器 URL。

其他入口：`make build` 只编译 Debug，`make release` 编译、签名 Release 并打包 DMG，不启动应用，`make test` 运行 Swift 测试，`make check-docs` 校验双语文档。两种构建共用 `build/Olanzi.app` 输出路径。若 Olanzi 已在运行，先从菜单栏退出再执行 `make dev`，确保启动新编译的版本；`open` 不会重启已有进程。

构建默认使用 Keychain 中唯一有效的代码签名身份。有多个时需显式选择；没有时会警告并退回临时签名。Debug 和 Release 应沿用同一身份，让重新编译后的签名要求保持稳定。本地自签名证书适合本地开发，不等于 Apple Developer 分发证书或公证。

```bash
make dev OLANZI_SIGNING_IDENTITY="Digger Local Signing"
```

变量也支持证书 SHA-1 指纹，或使用 `-` 显式选择临时签名。签名直接使用 Keychain 中的私钥，不导出私钥。macOS 可能要求允许 `codesign` 访问该密钥。

一步生成已签名的 Release 应用和可安装磁盘映像：

```bash
make release
# Equivalent alias
make dmg
# Explicit signing identity
make release OLANZI_SIGNING_IDENTITY="Digger Local Signing"
```

产物为 `build/Olanzi.app` 和 `build/Olanzi-<version>-<arch>.dmg`（目前 Apple Silicon 上为 `Olanzi-0.1.0-arm64.dmg`）。架构从编译后的可执行文件获取，不会自动生成通用二进制。DMG 内含应用与 Applications 快捷入口。打开后，将 Olanzi 拖入 Applications，再启动安装后的副本。替换前请退出正在运行的副本。

`tools/package-dmg.sh` 打包已有应用；通常应使用 `make release`，保证先重新构建。打包会用 App 的证书签名 DMG，校验映像校验和、只读挂载并检查包内应用签名与文件内容、检查 Applications 链接，卸载后才输出最终产物。临时文件自动清理；若卸载失败，则保留供恢复使用。不导出私钥。本地证书签名不等于 Apple 公证。

不接触真实硬件的隔离 UI 开发可使用：

```bash
swift run --package-path native Olanzi --demo
```

演示模式必须与真实设备会话在界面中明确区分。它模拟设备行为，不打开真实 HID 接口，也不注入系统 Fn 事件。演示预览成功不能证明真实设备写入或系统动作成功。

连接真实硬件前，退出官方 Studio，并停止仍在占用设备的旧工具。原生 App 不会替你杀死这些进程。插入接收器、打开 Vibe Key，再检查 App 的连接状态；接收器存在和设备本体在线是两种不同观察。

## 3. 窗口与菜单栏生命周期

点击菜单栏图标会展开紧凑状态面板，显示接收器/设备状态、电量、保活和权限或连接错误，并提供连接控制、暂停时恢复保活、一个始终打开 Driver 主页（键位页）的“设置”按钮，以及退出入口。

面板显示今日物理按键次数（含旋钮按下）、旋钮转动次数和活跃时间，以及七天活跃时间分布图。每次设备操作开启 30 秒活动窗口；重叠只计一次，只累计已过去的时间，断开、睡眠或退出会结束窗口。这是设备活动估算，不是 Mac 屏幕使用时间或语音输入时长。仅统计 Driver 运行期间从厂商通道观察到的事件；功能启用前或 Driver 停止期间的历史活动不可获取。没有记录的日期显示零。

按日汇总仅在本机保存，最多保留 30 天，不记录输入内容或音频。演示模式不读取或写入真实使用历史。存储失败会在面板提示，不中断按键转发。

红色关闭按钮和 `Cmd-W` 只隐藏配置窗口，保留草稿；Olanzi 仍留在菜单栏，Dock 图标隐藏，重新打开窗口时恢复。设备可用且保活未暂停时，后台设备线程继续维护连接、调度心跳和按已保存本机映射转发普通键与 Fn。需要修改键位时，可从菜单栏重新打开配置窗口。接收器连接期间，后台线程持有防止 App Nap 的活动声明，使心跳和输入处理不因窗口隐藏而被降低调度；断开或退出时释放，演示模式不申请。该声明允许 Mac 正常睡眠。

主窗口顶部只有 **键位** 和 **设置** 两个页面。设置页顶部为语言选择，下方集中显示 Vibe Key 状态、保活、连接帮助和键位配置管理；连接帮助始终显示，标题左侧为圆圈问号，不可折叠。可从顶部导航或 macOS 应用菜单“设置”（`Cmd-,`）打开，并通过语言选择器切换界面语言。选项为跟随系统（默认）、English 和简体中文；未支持的系统语言回退到 English。所选偏好会保存并即时生效，无需重启应用。切换语言保留键位配置和未保存草稿，用户自定义的配置名称与文件路径不翻译。权限欢迎页提供同一语言选择器，因此授权前也能切换语言，其余工作区仍由权限门控。

从应用菜单选择退出，或点击设置页左下角的红色关机按钮，才会停止 App 与设备线程。退出时会尝试释放合成 Fn 按住状态，并关闭设备接口。因此，关闭窗口与退出 App 是不同操作。电脑进入睡眠后，无论窗口是否打开，都无法持续发送心跳。

当前不安装登录项、`launchd` 服务或开机自启。需要时手动启动 App 即可；菜单栏常驻提供后台生命周期，无需另开 Python daemon。

## 4. 本机动作与心跳

1. 优先读取已有本机配置。文件不存在时，应用直接提供出厂键位草稿，不以设备旧键位作为来源，也不自动写文件。权限就绪后，无设备连接也可编辑该草稿，设备旧动作不会阻塞编辑。损坏的本机文件会保留，须修复后重启。
2. 在居中的设备示意图周围选择动作。旋钮两侧醒目的左旋、右旋箭头各对应一个旋转动作。右侧三个按键各有间隔清晰的独立卡片，旋钮按下则使用左侧卡片。每张卡片以三列显示单击、双击、长按，上方为手势名称，下方为当前动作；点击动作即可直接编辑对应控件及手势。
3. 检查所选动作。可选双击、长按均未设置时，保留主要按键立即响应。
4. 应用到本机。工作线程校验并原子保存整份配置，成功后才激活；此操作不写入设备键码。

选中键盘动作后，可独立于当前手势设置输出方式。**短按一次**发送一个脉冲，**连按**发送 2–20 次脉冲，默认 2 次；单击、双击、长按分别保存各自设置，仅连按显示次数。单击和长按还提供**保持按住**：只有单击时跟随实体按下/松开，长按则从阈值到达保持至松开。单击配置可选手势时等待判定，其保持按住模式在判定后发送一次脉冲。双击在松开时判定，旋转没有松开边沿，两者仅提供短按一次和连按。选项在主窗口内直接点击，不适用于切换 APP、宏或 MO；选择触发手势与选择输出次数是独立的编辑操作。

每次连按保持动作 40 ms，松开后间隔 80 ms 再按下一次。工作线程以非阻塞调度推进，延迟时延长间隔，不追赶补发。实体松开不取消已触发的一组，继续按住不重启整组。快速独立触发使用有界待执行队列。断连、睡眠、权限丢失或配置替换会取消待执行组及剩余脉冲，并释放当前动作。已有长按模式与次数保持原行为；新增单击设置默认保持按住、2 次，双击默认短按一次、2 次。模式和次数均编辑草稿，保存到本机后生效。单击、双击和旋转连按的实体输出仍待验证。

顶级键位、设备、配置、设置导航保持不变。键位页上半部的设备区域用于选择控件与手势，下半部用于选择按键。左侧导航包含常用、字符、功能键、数字键盘、组合键、Layer、APP、宏。常用包含导航与修饰键，字符包含字母、数字与符号；右侧显示可分配键帽，搜索覆盖全部按键。按钮统一使用深色圆角主题，并提供明确的悬停、禁用和主要动作状态。APP 与宏编辑在同一下半区域内完成。设备区域随窗口尺寸调整，按键选择区填满剩余高度；键帽按可用宽度排列，内容较多时可滚动浏览。手势卡片仅显示 M0 等宏编号，完整名称保留在动作库和悬停提示中。旋钮引导线指向旋钮中心，左右间距对称，两端均保留空隙。

在 APP 分类点击**添加 APP**，选择本机 `.app` 并保存命名库项，再点击 A0、A1 等键帽分配给当前手势。在宏分类点击**新建宏**，填写名称，组合 1–32 个顺序步骤：切换 APP、键盘组合或等待 0.05–10 秒；可新增、删除步骤及上移、下移。将宏保存到草稿库后，点击 M0、M1 等键帽分配。通过库卡片的编辑图标修改库项。引用为共享引用：编辑同一库项后，所有使用它的手势会在页面**保存到本机**成功后一起更新。被引用项不能删除，须先移除或替换这些手势绑定。

宏编辑器支持连续键盘录制、**可视化**与**代码**视图。连续录制将先后输入的组合键添加到宏中，记录间隔选项决定是否在组合键之间加入等待。切换 APP 可手动加入步骤，与录制的按键和等待自由组合。可视化修改生成代码；切回可视化或保存库项前，代码必须成功解析。解析或校验失败会保留输入文本及原步骤。保存库项仅更新草稿库，页面底部**保存到本机**才激活完整草稿。

录制序列时，在宏编辑器开始连续录制，依次按下并完全松开每组组合键，最后停止录制。开启记录间隔时，等待取上一组完全松开至下一组首次按下的时间，并四舍五入到毫秒；短于 50 ms 的间隔忽略，超过 10 秒则停止录制并保留完成步骤。按键与等待共同占用 32 步上限。手动停止或窗口失去焦点会丢弃尚未完成的组合，保留已完成步骤供检查。Esc、Enter 和 Command-Q 也会录为输入，须点击停止按钮结束。录制只捕获键盘输入，切换 APP 须随后手动添加。

要配置 Codex，在宏编辑器点击**填入 Codex 聚焦宏**，加入切换 `com.openai.codex`、等待 0.8 秒和 `⌃⌥⌘I`。将命名宏保存到草稿库，点击其 M 键帽分配给目标手势，再保存到本机，即可直接使用原 Raycast 脚本的快捷键流程。执行时驱动按需启动目标应用，并等待前台确认。切换 APP 和宏在手势判定后执行一次，持续长按不会重复触发。激活失败或选定应用失去前台时停止后续宏按键；断连、睡眠、权限丢失、配置替换或退出会取消待执行动作。

代码支持 [QMK 宏语法](https://docs.qmk.fm/feature_macros)与受支持的 [QMK 键码](https://docs.qmk.fm/keycodes)子集，不接受完整 C 源码或固件。输入顺序语句即可，例如这段 Codex 流程：

```c
OLANZI_APP("com.openai.codex");
wait_ms(800);
tap_code16(LCTL(LALT(LGUI(KC_I))));
```

`OLANZI_APP` 是 Olanzi 扩展，不是 QMK 函数。它接受单独的 bundle identifier，或恰好三个参数：bundle identifier、应用路径与显示名称；示例只填 bundle identifier，会查找本机已安装应用。`OLANZI_FN` 是 Olanzi 表示 Mac Fn 的键常量。这些扩展通过主机驱动执行，不修改固件。

| 支持的代码 | 含义与限制 |
|---|---|
| `tap_code(KC_A);` | 发送一次受支持基础键的脉冲。 |
| `tap_code16(LCTL(LALT(LGUI(KC_I))));` | 发送带嵌套 Control、Shift、Alt/Option 或 GUI/Command 修饰键的按键；同一 `tap_code16` 表达式不能混合左右侧修饰键。 |
| `wait_ms(800);` | 等待整数 50–10000 毫秒。 |
| `SEND_STRING("Hi");` | 按 US ANSI 键位展开受支持 ASCII，不是 Unicode 文本注入，输出取决于当前键盘布局。 |
| `SEND_STRING(SS_TAP(X_I) SS_DELAY(800));` | 展开受支持的按键脉冲与等待；`SS_LCTL(...)` 等修饰包装仅可作用于单键，内部不能含等待。 |
| `register_code(KC_A); register_code(KC_B); unregister_code(KC_B); unregister_code(KC_A);` | 表示同时按住的多键组合；按下须构成同一组，随后逆序松开，中间不能插入等待或交错动作。 |

未知或不支持的语法会报告行列位置，不执行。编辑器最多接受 32 KiB 代码与 32 层嵌套，展开结果仍须满足 1–32 个宏步骤的上限。视图转换保留可执行步骤，不保留原空白、注释或等价语法的具体写法。

设备示意图和动作卡片用于选择控件，不再另列重复控件列表。按键面板固定提供 **▽** 和**带叉圆角正方形（`xmark.square`，不执行动作）**，替代独立的清除动作与恢复继承按钮。非基础层的 ▽ 只恢复当前手势的底层动作、输出模式与次数，保留其他覆盖；Layer 0 不允许继承。带叉正方形键帽将单击设为显式无动作，或关闭当前双击/长按使其不参与识别，即使底层配置了该手势也不再使用。继承动作显示下三角箭头，悬停与无障碍文字说明其含义；时序与 Fn 说明收在问号帮助中。页底仅显示待保存或保存中的状态，不常驻已保存标签，异常仍可见。设置页的连接帮助始终显示，标题左侧为圆圈问号，不显示心跳计数。

保存等操作反馈改为窗口顶部悬浮的胶囊提示，使用两端为半圆的 `Capsule`，不占据页面布局空间。短提示约 3.5 秒后自动消失，长提示保留 7 秒，也可手动关闭；连续相同提示会重新计时。

配置组合键时，先在上半设备区域选择控件与手势，再在下半分类选择**组合键**，点击**录制组合键**。同时按住需要组合的按键，例如 A+B 或 Control+A+B，全部松开后完成并预览；也支持纯修饰键组合及 Fn，Caps Lock 仍从普通按键分类选择。左右修饰键统一保存为左侧修饰键。录制组合键开始新的尝试，取消录制丢弃本次录制；**分配组合键**将结果写入所选手势草稿，再保存到本机生效。切换控件、手势、分类或离开 App 都会停止捕获。组合键表示同时按住多个键，不是带时序的宏；系统占用的快捷键可能被 macOS 优先处理而无法录制。

Olanzi 保活与转发运行时，本机映射负责全部六个控件，包括普通键与 Fn。已有映射或新的默认草稿均可离线编辑，新草稿仅在显式保存成功后生效；设备刷新与重连不会覆盖它。保存和导出的版本 2 `HostProfile` JSON 包含主要动作、双击、长按动作、各手势的键盘输出方式与连按次数、时间参数、APP 目标、命名库项及其共享引用，以及完整宏步骤。双击和长按继续保留；跨 Mac 搬移完整配置时，在一台 Mac 导出，在另一台导入后显式保存到本机，不提供通过设备自动跨 Mac 同步。旧原生六键配置迁移为主要动作。职责、时序和迁移细节见 [10 · Daemon 输入运行时](10-input-runtime.zh.md)。

导出默认文件名为 `vibe-key-yyyy-MM-dd_HH-mm-ss-SSS.json`，使用当前本地日期和时间，精确到毫秒，方便区分连续导出的文件。

设置页的“键位配置”区域提供可选的“从设备键位导入”操作，先校验只读快照中的六个控件，成功才载入草稿。不支持的动作会指出具体控件，并保留当前草稿；导入本身不会保存或激活草稿。设备键位表保留为独立回退。协议工具的显式硬件写入仍需 ACK 与回读，并可能部分成功；原生本机动作编辑器不再调用该操作。草稿、本机已保存映射与硬件快照三者相互独立。

心跳使用从 Studio 恢复的明文前缀 `06 01 23 00 01`，后补零。它会选择厂商事件转发方式，因此只有本机配置已成功保存且有效、设备已连接且在线、输入监控与辅助功能权限就绪并且未暂停输入时才启用。条件不满足时停止心跳，继续允许只读在线和键位查询；查询等待期间也检查权限与睡眠状态。发送成功本身不能证明无线送达或长时间不休眠。见 [07 · 心跳调查](07-heartbeat-investigation.zh.md)。

设置页的 Vibe Key 区域提供空闲停止保活选项：**永不**（默认），或 **1、5、10、15、30、60 分钟**。修改立即保存到本机，独立于键位草稿与配置。仅 Vibe Key 的物理按键和旋钮动作计为活动；控件按住期间不会超时，松开后开始新的空闲计时。状态与电量查询、电脑其他输入和隐藏窗口均不重置计时。

超时后，工作线程停止心跳，取消主机手势、临时 Layer、键盘连按和宏，并释放合成按键。设备可能恢复自身固件键位。暂停期间收到物理操作后，会在全部控件松开并排空 100 ms 的尾随报文后自动恢复主机转发；唤醒动作不补发，以免标准 HID 已直出时双发。可从设置页或菜单栏点击**恢复保活**；接收器真正重连、Mac 唤醒或已确认的设备离线转在线也会重新计时。查询失败导致的未知状态恢复在线不会解除暂停。设备真实休眠时间和省电效果仍需实测。

空闲暂停同时停止每两秒的后台在线查询和每 20 秒的电量查询，仅保留接收回调与 USB 移除检测，避免后台通信干扰设备自身的待机与休眠计时。界面在线状态和电量是暂停前的最后读数，不是当前清醒的证明；暂停期间额外被动监听 AU05 标准 HID 接口，只接收设备输入，不发送查询；厂商事件和标准 HID 活动均可触发自动恢复。普通电脑键盘不会触发恢复。若监听权限不足或接口异常，会报告错误，也可点击**恢复保活**。显式连接检查或刷新仍会发送请求，但不会仅因查询成功解除暂停。停止保活不会修改设备内的待机或休眠时长，也不代表立即休眠；具体时长与实际省电效果需真机验证。

空闲暂停采用 VibeKey Lite 的主机控制交接方式：停止心跳后同步发送 `01 01 10 00 00`（软件离线），恢复时先发送 `01 01 10 00 03`（软件在线），成功后才允许心跳。发送均由同一设备工作线程串行完成，不在 HID 回调里写设备。断开、退出及 Mac 睡眠也会尝试交还控制；交接失败会显式报错并停止接管，可点击恢复保活重试。该流程不修改设备内的灯光、待机或休眠配置，旋钮熄灯和实际休眠时间仍待真机验证。

主窗口右上方在连接状态下显示电量。设备在线且未因空闲暂停时，工作线程每 20 秒发送只读 `01 01 02 01` 查询，并记录最近成功更新时间；界面显示百分比和充电状态，20% 及以下用橙色标注。离线、未知或读取失败时显示 `电量 —`；仅百分比不可用但电压有效时改为显示电压。悬停提示包含电压、更新时间或独立读取错误。电量失败会清除旧读数并在下一周期重试，不停用 Fn 转发。解码依据见 [02 · 协议](02-vibekey-protocol.zh.md#电量回复字段)，当前样本与验证边界见 [05 §9.10](05-verification-log.zh.md#910-只读电量状态与主窗口显示)。

## 5. 厂商按键转发、Fn 与权限

[CONFIRMED] 2026-09-21 现场对照发现：Olanzi 每秒发送 Studio 心跳时，普通键不再标准 HID 直出，Fn 标准输入回调也无报文。仅关闭 Fn 输入接口无效；仅停心跳、保留厂商连接和只读查询后，Enter 恢复。此时按键从厂商通道以 `8b 10` 上报，详见 [07 §4](07-heartbeat-investigation.zh.md)。因此普通键和 Fn 都需要应用侧转发及相应权限。

`GestureRouter` 按物理控件索引与已保存本机映射识别手势，`VendorKeyBridge` 执行选定的键盘动作、切换 APP 或宏。`frame[2]` 的逻辑动作号不是 HID 键码，不能直接注入；AU05 的物理 index 来自 `frame[4]`。未应用草稿不参与转发，未知或多媒体映射须明确报错，不猜测注入。六个物理控件的 index 与旋转方向已现场确认；旋转 index 4/5 仅上报按下，由主机补松开形成脉冲。前一版厂商转发通过 68 项自动化测试与签名 Release 构建，本机运行时检查见 [10](10-input-runtime.zh.md)；该早期版本确认了 Enter 和顶部 Fn 的物理效果。后续旋钮到 F13 的测试确认了此前 Raycast 脚本聚焦输入框的动作，见 [10 §4](10-input-runtime.zh.md#4-按住取消与失败处理)。这些结果不代表每个控件、应用动作或新的 Codex 直达宏都已验证。

Fn 仍是修饰键类别里的普通键名，选择并应用即可，没有独立功能开关或 `macFnEnabled` 设置。设备键码 `0x01` 在主机映射中表示 Fn，出厂顶部键也使用它。厂商事件包含物理控件 index，因此旧标准 HID 原型“同码物理键不可区分”的限制不能直接套用到新路径。移除全部 Fn 映射只是不再生成 Fn，普通键转发仍需运行与授权。

在“系统设置 → 隐私与安全性”里，给 **Olanzi App** 同时授予输入监控与辅助功能权限。这是原生应用包的权限，不是旧终端进程的授权步骤。非演示模式缺少任一权限时，只显示 App 主窗口内部的权限欢迎页，通过替换窗口内容实现，不另开弹窗、窗口或 sheet，也不进入配置工作区或设置界面，也不堆叠初始化错误与页底错误栏。欢迎页提供输入监控、辅助功能两项授权引导、对应系统设置按钮及 App 位置入口；权限提示与本机配置是否初始化、设备是否在线独立。两项权限都就绪后自动进入工作区；撤销权限后返回欢迎页。演示模式不受此门控影响。欢迎页门控相关自动回归、构建与真实界面验证已通过：单个 Olanzi 主窗口内显示欢迎正文、两项权限状态及设置和 App 位置入口，没有配置导航、初始化错误、保存页底栏或额外弹窗。点击先在应用主线程直接请求所选权限，再打开对应系统设置；请求不再等待设备线程或连接。输入监控先使用 HID 请求接口，仍未获准时再调用事件监听请求作为后备。一次请求一项权限，不增加单独的 Fn 功能面板。系统策略和已有拒绝记录仍可能阻止再次弹框；打开设置页本身不能证明应用已加入列表。App 每秒无弹框检查一次权限，不依赖返回或激活窗口，也不等待设备工作线程。界面单独保存轮询结果，避免较旧设备快照覆盖新权限状态；变化后自动切换欢迎页与工作区，并通知设备服务复查。停止应用时取消定时器，演示模式不轮询。若系统设置已开启但运行进程仍报告不可用，请先核对获授权的 App 副本与路径；不能仅凭设置开关宣称当前进程已获准。普通键和 Fn 的转发均受此权限状态约束；有设备映射不代表权限已就绪或转发已成功运行。

输入监控先读取 `CGPreflightListenEventAccess()`；若为假，再尝试创建 session 层、listen-only、仅包含 key-down/key-up 的短暂事件 tap，以验证当前进程的键盘监听能力。探针须同时有效且已启用，并立即 invalidate、释放，不加入 run loop，不收集键盘内容。`IOHIDCheckAccess()` 与事件合成预检保留作诊断；辅助功能每次独立读取 `AXIsProcessTrusted()`，不再被其他预检结果短路。日志包含 `ListenProbe`，区分实际探针结果与未执行。界面据此显示当前监听能力“已就绪”，不等于读取系统设置中的单独开关，也不证明权限 API 的缓存机制。此前 §9.5/§9.6 的仅预检判定和有条件 AX 检查已由新方案替代；原位证据及验证边界见 [05 §9.7](05-verification-log.zh.md#97-预检拒绝时验证实际键盘监听能力)。

新转发路径消费已有厂商连接的按键事件，不依赖没有报文的 Fn 标准输入回调。所有按键转发都需要 App 持续运行、设备在线、有效已保存本机映射和相应权限。关闭窗口后仍继续，退出 App 则停止。实现须按物理控件跟踪按住状态，避免重复按下，并在松开、断连或退出时尝试释放；Enter 和一对顶部 Fn 的按下/松开已有早期现场验证，不能据此推定所有控件与异常释放场景都已物理验证。

Fn 转换不是固件原生 Fn 命令；协议或模拟事件测试均不能证明它与 Apple 硬件 Fn/地球键等效。听写、输入源切换、Studio 专用 Fn 路径和应用特定动作仍需物理测试。触发码原理与旧原型实现见 [08 · Mac Fn](08-mac-fn.zh.md)，其中的 Python 命令和 HTTP 设置不适用于原生 App。

原生转换通过 `cghidEventTap` 投递 Fn，保留私有事件源和成对的 `flagsChanged` 事件。[CONFIRMED] 检查运行中的豆包输入法发现其监听器位于 HID 层，Studio 的通用键盘事件发送路径也向这一层投递。此前会话层注入绕过了位于更早阶段的监听器。改为 HID 层投递修正了这一位置差异；早期现场测试确认顶部 Fn 能唤起豆包，日志也记录了松开后的 Fn 位清除；这一结果限于下述历史测试。这只解释了投递层级差异；新的心跳对照进一步确认，普通键失效还涉及从标准 HID 切换到厂商事件，不能仅靠改 Fn 的投递层级解决。普通键与 Fn 转发仍共同采用 CoreGraphics 私有事件源和 HID tap。私有事件源不能隔离 `.hidSystemState`：后续原位测量发现，`flagsState` 和 `keyState` 都包含本应用合成 Fn 的反馈。`PhysicalFnMonitor` 现在通过 session 层 listen-only `flagsChanged` tap 跟踪真实 Fn 与左右 Control、Shift、Option、Command；只接受来源 PID 0，并只更新当前虚拟键码对应的侧键，避免从无关标志继承合成反馈。初始缓存为空，不从系统汇总状态取种子；`VendorKeyBridge` 在转发前准备监听，失败时停止转发并报错。主路径 `MacKeyEmitter` 从汇总状态中清除这些修饰键的家族位与侧位，再合并监听缓存及本应用持有的动作；Caps Lock 等其他状态仍按原路径处理。旧原生后端仍使用该监听器提供的 Fn 状态。tap 中断时清空失去可信度的缓存并尝试重新启用，不等待用户按键而无限暂停；下一个真实侧键事件重建该侧状态。启动前或漏报窗口中已按住的真实修饰键需要松开再按。监听仅读取修饰键元数据，析构时移除并释放 run-loop source 与 tap。2026-09-22 的 00:42:57/59 的日志已观察到一组真实 Fn 的 PID 0 按下/松开，只验证该组事件，不代表所有键盘交错场景，见[修饰键反馈摘录](evidence/2026-09-22-modifier-feedback.log)。原先仅隔离 Fn 的修订见 [05 §9.9](05-verification-log.zh.md#99-合成-fn-反馈污染-hid-状态)；修复后的两轮实测及其边界见下文。

需要持续按住 Fn 时，把单击映射为 Fn、选择保持按住并关闭可选手势，按住状态持续至松开；长按映射为 Fn 且选择保持按住时，超过阈值后开始保持，松开时结束；短按一次在阈值处发送一次 Fn 脉冲，连按则发送指定次数的 Fn 脉冲；两者都不会因持续按住而重复整组。单击 Fn 与其他手势并存、或双击映射为 Fn 时，手势判定后按所选输出模式执行一次或多次脉冲，此时单击保持按住转为一次脉冲，界面会解释这一区别。这些是运行时动作语义，不能证明输入法的实际响应。

本机诊断使用 `com.mrcroxx.olanzi` 日志子系统的 `device-input` 类别。排查时先区分厂商帧、解码后的物理控件按下/松开、已保存本机动作和主机事件发送；没有标准输入回调本身不能再当作设备没有按键的证据。六控件事件及 Enter / Fn 的验证摘录见[厂商按键路由记录](evidence/2026-09-21-vendor-key-routing.log)。六控件采集确认索引与按下/松开形状；该历史样本还确认了 Enter 与顶部 Fn 的现场系统效果。后续 [F13 验证日志](evidence/2026-09-22-f13-hotkey.log) 记录了旋钮触发 Raycast 脚本及用户对输入框聚焦的确认。“待应用”草稿不是生效配置，测试前须保存到本机并等待激活。
