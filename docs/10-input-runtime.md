## 1. Ownership and scope

All six controls enter one host input pipeline. The menu-bar application's device worker owns the receiver, heartbeat, gesture clock, committed action map, and generated key holds. The window edits drafts and submits configurations; closing it does not stop the worker. This is an in-process background service, not a separately installed launch daemon or login item. Quitting the app stops forwarding.

The previous implementation looked up each event in the device's key table. That conflated the hardware fallback with runtime actions and had no place to recognize double presses or long presses. The runtime now loads the persistent host configuration first. A missing file makes the UI offer its own default draft; the worker does not seed from device mappings or write a file automatically. Device snapshots remain independent, and refreshes and reconnects do not replace the host configuration or draft. Normal edits never issue a hardware key-table write.

| Layer | Responsibility |
|---|---|
| `MacHIDTransport` | Decode vendor frames and deliver physical-control edges, including while a query is waiting |
| `GestureRouter` | Interpret edges and monotonic deadlines; choose exactly one configured action |
| `VendorKeyBridge` | Route selected actions, execute keyboard holds, preserve shared modifiers, and retry failed releases |
| `HostActionRunner` | Advance app activation and ordered macro steps without blocking the device worker |
| `MacKeyEmitter` | Translate keyboard usages to macOS events and post at the HID tap |
| `PhysicalFnMonitor` | Track physical Fn metadata independently of aggregate synthetic-event feedback |
| `HostKeymapStore` | Validate and atomically persist the authoritative host configuration |
| SwiftUI / `AppModel` | Edit drafts, choose gestures, import/export profiles, and submit saves |

Vendor events identify controls independently of their configured actions. The AU05 physical index is `frame[4]`; `frame[2]` is a logical action number and is never injected as a keyboard usage. The four push controls send press/release edges. Rotary controls 4 and 5 send a press-only pulse per tick. See [the routing capture](evidence/2026-09-21-vendor-key-routing.log).

## 2. Actions and timing

Each control has a primary `press` action. The four push controls may additionally configure `doublePress` and `longPress`. Each action selects keyboard entries, an app target, or an ordered macro; push controls can also assign MO to their primary or long-press action, as described below. The keyboard picker assigns one key to the chosen action, while the compact recorder assigns combinations that can include multiple ordinary keys and modifiers. Gesture recognition and keyboard output mode are independent: each of primary, double press, and long press can select `tap` (Tap Once) or `burst` (Repeat), with its own 2–20 count, defaulting to 2. Primary and long-press actions additionally offer `hold` (Hold). Primary-only Hold follows physical press/release; long Hold starts at the threshold and ends on physical release. A primary with optional gestures waits for recognition, and its Hold mode emits one pulse when recognized. Double press is recognized on release and supports only Tap Once or Repeat; rotary ticks also offer only those pulse modes and reject double/long gesture mappings. The inline count stepper appears only in Repeat mode. For a gesture without an inheritance flag, an absent optional action disables that gesture; the No Action keycap creates this explicit override for double/long press, or an intentional no-op for primary press. A gesture marked transparent instead inherits its action, output mode, and count from lower active layers. App switches, macros, and MO do not use keyboard output modes or repeat counts; app switches and macros run once per recognized gesture.

An app action identifies a local application selected through the `.app` picker. Execution launches it if needed, requests activation, and waits until it is confirmed as the foreground application before continuing. Macros contain 1–32 non-nested steps, each an app switch, a keyboard combination, or a wait of 0.05–10 seconds. Steps execute in their configured order; keyboard steps emit a pulse rather than remaining held for later steps. The editor can add, delete, and reorder steps. App actions and macros execute serially. For app and macro execution, a control can have at most one queued or running action, and the global queue plus running action is capped at eight; extra triggers are ignored. Keyboard macro steps hold keys for 40 ms, and app activation must complete with foreground confirmation within five seconds. Neither waits nor activation block heartbeat processing.

Open the Macros category in the lower key picker, create a named macro, and choose **Fill Codex Focus Macro**. The template fills the editor with an app switch to `com.openai.codex`, a 0.8-second wait, and `⌃⌥⌘I`. Save the library item, assign its M keycap to a gesture, and explicitly save the complete draft to this Mac. The wait can be adjusted for the target application; foreground confirmation does not prove that a specific input field is ready. The new direct workflow still requires physical and target-application verification.

The editor places distinct gesture cards around a centered device illustration: one card for each of the three keys on the right and one for knob press on the left. Each card has three columns with the gesture name above its action; clicking an action selects that control and gesture. Left/right rotation arrows flank the knob and each expose only a primary action. There is no duplicate control list. Detailed timing and Fn explanations are available through question-mark help; normal operation omits saved-state labels and heartbeat counters while keeping errors visible.

| Configuration or event | Behavior |
|---|---|
| No optional gesture | Primary keyboard Hold follows physical press/release immediately; Tap Once or Repeat starts its pulse group immediately. Other action types start once immediately. |
| Ordinary primary with long press only | Release before the threshold runs the selected primary output mode (Hold becomes one pulse); reaching the threshold executes a keyboard long action using Hold, Tap Once, or Repeat, starts an app switch or macro once, or holds a long-press MO layer until release. |
| Primary MO with a long action | The primary layer activates immediately; the long action runs at its threshold. Long-press MO replaces this control’s layer activation; other long actions leave it active until physical release. |
| Double press configured | The first release waits for the double-press window; expiry runs the selected primary output mode (Hold becomes one pulse). |
| Second down before the double deadline | Claims the second press; its release runs the double action using Tap Once or Repeat for keyboard output. |
| Second press reaches the long threshold | A configured long action takes precedence; neither the pending primary nor double action is emitted. |
| Second down exactly at or after the deadline | The first primary expires first; the new down starts another gesture. |
| Rotary tick | Trigger the primary action immediately; keyboard output uses Tap Once or Repeat without waiting for a device release. |

Repeat schedules each action down for 40 ms, then leaves an 80 ms gap from up to the next down. Each recognized primary, double press, long press, or rotary tick starts one group using that gesture's configured count. Physical release after it starts does not cancel the remaining group, and continuing to hold does not start another group. Each control allows one running keyboard action and at most 16 pending actions in FIFO order. When full, the newest trigger is dropped without interrupting the active down/up pair. Existing long-press repeat handling continues to quarantine repeated physical-down edges rather than treating them as new long gestures. Scheduling does not block the worker; a delayed worker advances one edge at a time and schedules the next deadline from actual advancement, rather than catching up with overdue pulses. Input suspension, disconnect, sleep, permission loss, configuration replacement, or an execution error cancels pending groups and remaining pulses and attempts to release active keys. Physical primary, double-press, and rotary repeat behavior remains to be verified.

The default double-press window is 250 ms from the first release; the long-press threshold is 500 ms from the relevant press. Configuration accepts a double window of 150–500 ms and a long threshold of 300–2000 ms, with the long threshold greater than the double window. The clock is monotonic. Duplicate down packets do not restart a hold or deadline.

Enabling an optional gesture delays an ambiguous ordinary primary action; primary MO remains immediate even with a long action configured. Choose primary Hold and keep optional gestures disabled on a control that must immediately act as a held Fn, Shift, or other modifier. A long action mapped to Fn with Hold begins holding Fn only after its threshold and releases when the control is released; Tap Once emits one Fn pulse at the threshold, while Repeat emits the configured number of pulses; continuing to hold does not repeat either group. Primary Fn with another gesture enabled, and double-press Fn, use the selected single or repeated pulses after gesture recognition; primary Hold becomes one pulse in this case. The UI explains continuous holds versus pulses; an input method’s actual behavior still requires physical verification.

### 2.1 Momentary layers

The four fixed layers are numbered 0–3 and have no custom names. Layer 0 always provides the complete six-control base mapping and cannot inherit. Layers 1–3 are available immediately and transparent by default. A missing control record inherits all of its gestures; an existing record can mark primary, double press, and long press transparent separately. Resolution checks each gesture through active layers from highest number to lowest and finally Layer 0, inheriting that gesture's keyboard output mode and count with its action. An explicit No Action primary action is a no-op, while No Action double/long press disables that gesture and prevents recognition of the lower-layer gesture. Neither is transparency. Existing control records without inheritance flags retain their complete control override, including disabled optional gestures.

The **Layer** category assigns **MO(n)** to the primary or long-press action of any of the three keys or knob press. Primary MO immediately activates its target without waiting for a threshold. Assigning primary MO clears double press but preserves the long action; MO is not available for double press, rotary ticks, macros, or action-library items. MO targets are limited to layers 1–3; an unedited target is valid even when it has no stored layer record. Multiple held controls targeting one layer keep it active until the last holder releases. Simultaneously active layers use numerical priority, not activation order.

Primary MO can coexist with a keyboard, app, or macro long action. At the configured threshold, the long action runs with the existing keyboard Hold, Tap Once, or Repeat behavior, or starts the app switch or macro once. The primary MO activation remains until physical release. Releasing the control immediately removes that activation even if an already-started keyboard repeat group continues its remaining pulses. If the long action is also MO, the threshold replaces only this control's primary layer activation with its long target; other controls' activations remain intact.

An ordinary primary action can instead be paired with long-press MO: release before the threshold follows normal single/double recognition; reaching the threshold activates the long target until release and suppresses the pending primary or double action. Existing double-press mappings can coexist with this configuration and retain their normal timing. Long-press MO always waits for the configured long-press threshold, including when another control is pressed in the meantime; another press does not force an early hold decision. Keyboard Hold, Tap Once, and Repeat options do not apply to MO.

Each physical press resolves and retains its control mapping for the complete hold or gesture sequence, including a pending single/double decision. Changing layers while another control is held does not replace its action or redirect its release. A new rotary tick resolves the current active layers independently. Layer cancellation clears all activations along with gesture and key cleanup; a canceled held MO control must be released before it can activate a layer again.

The **0 1 2 3** buttons are always visible in one row above the device. Click a number directly to edit its layer. Inherited primary/double/long actions and both rotary directions show a VIA-style downward triangle (`arrowtriangle.down`), with hover and accessibility text identifying inheritance from a lower layer. The key picker always includes **▽** and a **rounded square with a cross (`xmark.square`)** (No Action), replacing separate clear-action and restore-inheritance buttons. On a non-base layer, ▽ makes only the selected gesture transparent and preserves its siblings' overrides; Layer 0 cannot use it. The crossed-square keycap sets a primary no-op or disables the selected double/long gesture. Editing a layer previews its controls without activating that layer in the input worker. Library references and MO target numbers are checked across every layer. Layer edits stay in the draft and take effect only after **Save to This Mac** succeeds.

For example, click **1** and override key 2 and knob rotation, then click **0** and set key 1's primary action to MO(1). Save to this Mac, then hold key 1 while using those controls. Releasing key 1 restores the remaining active layers for new presses; if key 2 is still held, it finishes its Layer 1 action on release. This is host-side momentary switching with optional threshold-based long-press layer actions; toggle layers are not part of this implementation. Physical Layer combinations and their long-press behavior on the AU05 remain to be verified.

## 3. Configuration and migration

The active map is stored at `~/Library/Application Support/Olanzi/host-keymap.json`. It contains six unique control indices, the action entries, timing values, and schema version. The store validates before writing, uses an atomic replacement, and does not activate a new map when persistence fails. If the file is missing, the worker publishes `hostConfigurationMissing=true` without creating a map or writing a file. The app offers `HostKeymap.defaultKeymap` as an editable draft, independent of device presence or the types in its old key table. A corrupt or unsupported local file remains an error, requires repair followed by an app restart, and cannot be overwritten by a draft. Only an explicit successful save persists and activates a new host map; until then, the default draft does not enable heartbeats. This process never writes the device key table.

The device table is a separate fallback used when the app is absent and the receiver returns to standard HID output. Editing the fallback remains an explicit protocol-tool operation described in [03 · Tool Manual](03-tool-manual.md). Applying a host map or importing a profile does not rewrite it. The Key Profiles section in Settings can explicitly import the read-only device key snapshot into a draft. All six controls must validate; a failure identifies the affected control and preserves the existing draft. This optional import is not initialization or activation. Default drafts and existing host maps can be edited and saved offline; demo mode uses memory only and never touches the real host store or device.

Exported `HostProfile` version 2 includes every control’s `press`, optional `doublePress` and `longPress` actions, the `pressBehavior`/`pressTapCount`, `doublePressBehavior`/`doublePressTapCount`, and `longPressBehavior`/`longPressTapCount` keyboard output settings, and the `doublePressWindow` and `longPressThreshold` timing values, together with app targets and complete macro steps. Existing keyboard-only actions remain compatible. The outer profile stays at version 2. Its nested `HostKeymap` writes version 5 when new primary or double-press output settings differ from their defaults or any gesture inheritance flags are present. Each control’s `inheritedGestures` is a `Set<ControlGesture>` containing any of `press`, `doublePress`, and `longPress`; marked gestures inherit their actions and keyboard output settings. No Action primary is stored as keyboard key 0, while No Action double/long press is `nil` without an inheritance flag. A missing control record inherits all gestures; an existing record without flags keeps its legacy complete override. Without non-default output settings or inheritance flags, existing version selection remains unchanged: layer overrides or MO actions use version 4. Storage remains sparse: unedited layers 1–3 may be absent from `layers`, and MO(1)–MO(3) remain valid without corresponding stored records. The reader accepts map versions 1–5, preserving older keyboard mappings and inline app/macro actions as Layer 0 with transparent layers 1–3. When no version-5 settings, layer records, or MO actions are present, serialization retains version 3 for an action library or library references, version 2 for other extended actions, and version 1 for keyboard-only mappings. Missing `pressBehavior` and `pressTapCount` default to `hold` and 2; missing `doublePressBehavior` and `doublePressTapCount` default to `tap` and 2. Older profiles without `longPressBehavior` decode as `hold`, and a missing `longPressTapCount` defaults to 2. Existing long-press modes and counts are retained; a rotary primary with legacy `hold` still executes one pulse. Existing Hold and Tap Once profiles retain their behavior; the count is validated within 2–20 in every mode. Rotary controls do not support long-press behavior. Double/long gestures remain supported. The chosen cross-Mac workflow is to export this complete JSON, import it on the destination Mac, and explicitly save it locally. Automatic cross-Mac synchronization through the device is not provided, and profile transfer never writes the device key table. Import accepts legacy native version-1 six-code profiles by turning their codes into primary actions with optional gestures disabled. Saved profile collections use `nativeHostProfiles`; the old `nativeProfiles` collection remains available as the migration source. Entries are decoded and migrated independently, so one corrupt or unsupported entry cannot prevent valid profiles from loading. Complete original data containing failed entries is backed up in `nativeHostProfilesRecoveryBackups`; subsequent profile saves or deletions do not overwrite that recovery copy. Import is bounded to 32 KiB and rejects invalid versions, duplicate/missing controls, unsupported keys, invalid timings, and rotary gesture mappings.

Version 3 adds `actionLibrary`, whose `NamedHostAction` entries have a stable UUID `id`, a 1–80-character `name`, a numeric `slot`, and an app or macro `action`. Apps use A0–A15 and macros M0–M15; slot allocation is independent for each category. Control actions reference an item by its UUID, and the runtime resolves the reference against the committed map. Library items cannot reference other library items or contain standalone keyboard actions. Validation rejects missing references, duplicate IDs or same-category slots, and invalid names or actions. Unassigned items are saved and exported too. Editing an item preserves its identity and updates all references after local save; deleting a referenced item is rejected until all its bindings are removed. Library edits, assignments, and deletions share the same draft and atomic-save boundary.

The lower picker’s Combinations category records a simultaneous group through the same host-map workflow, including A+B, Control+A+B, modifier-only combinations, and Fn. Releasing all keys finishes the group and displays its preview. This single-combination recorder does not save macro timing; continuous recording in the macro editor uses `MacroRecordingSession` to collect successive completed groups and optional gaps. Left and right modifiers are normalized to their left-side forms; Caps Lock remains selectable through the regular key categories. **Assign Shortcut** replaces the selected gesture draft, and the map becomes persistent and active only after explicit local save succeeds. Switching the selected control, gesture, or category, or leaving the app, stops capture. System-reserved shortcuts may not reach the recorder. See [09 §4](09-native-macos.md#4-host-actions-and-heartbeat) for the recording steps.

Starting a shortcut recording activates its owning window and moves keyboard focus to the recording area; the idle view says Not recorded, recording shows Recording, and incoming keys update the preview live. Completion is published independently, so a quick press and release still produces an assignable preview. After a brief event-free interval, release reconciliation checks only already-captured keys and modifiers; polling never adds keys to the chord.

Macro Code is an editor representation of the same `[MacroStep]` values used by Visual mode. `QMKMacroCodec` parses only its supported QMK statement subset; it does not compile C, run arbitrary functions, or interpret firmware state. App switching and Mac Fn use explicit Olanzi extensions. Parsing and step validation finish before replacing the editor sequence, so invalid code leaves both the input text and prior actions intact. Successful conversion does not activate the map: saving the library item updates the draft, and the page footer’s local save remains the persistence boundary. Code text, comments, and formatting are not a second stored macro format. Supported syntax and the Codex example are documented in [09 §4](09-native-macos.md#4-host-actions-and-heartbeat).

The interface-language preference is independent of the host map and exported profiles. Follow System defaults to English when the system language is unsupported; English and Simplified Chinese can also be selected explicitly. Switching language updates the interface immediately and saves the preference without replacing the active map, discarding draft actions, or translating user-defined profile names and file paths. See [09 · Native macOS App](09-native-macos.md#3-window-and-menu-bar-lifecycle) for the Settings and permission-welcome-page entry points.

Each save has a distinct request ID and returns its matching success or failure in the snapshot. The UI ends its pending-save state only for that request, rather than treating busy-state changes from refresh or reconnection as save completion. Further draft edits made during the save remain intact.

## 4. Holds, cancellation, and failures

An emitted hold owns a snapshot of its action. Shared macOS keys are reference-counted across controls, including aliases such as Print Screen and F13; releasing one control must not release another control's key. Other active modifiers remain present in emitted flags. Every rotary tick receives a host-generated release.

[CONFIRMED] F1–F20 down and up events also carry their own function flag. This shares a bit with physical Fn but does not represent an additional Fn hold. See Apple's [function flag documentation](https://developer.apple.com/documentation/appkit/nsevent/modifierflags-swift.struct/function). Investigation of an F13 hotkey on 2026-09-22 found that the old emitter omitted this bit when overwriting event flags; two new regression tests failed before the fix. The emitter now adds it by macOS virtual key, including Print Screen and other F13–F15 aliases, without registering them as held modifiers. Subsequent ordinary keys and Fn releases still clear synthetic feedback. All 173 tests passed after the fix, and the build was signed with the existing Keychain identity. Physical logs captured F13 events corresponding to knob presses and releases, alongside successful Raycast script runs at matching times. The user confirmed that both attempts focused the input field. This verifies the current script and configuration, not every application hotkey. See the [raw F13 verification log](evidence/2026-09-22-f13-hotkey.log).

`PhysicalFnMonitor` now tracks physical Fn and both sides of Control, Shift, Option, and Command through a session-level, listen-only `flagsChanged` tap. It accepts source PID 0 and updates only the side identified by the event’s virtual keycode, without inheriting unrelated flag bits or seeding from aggregate system state. The cache starts empty. `VendorKeyBridge` prepares monitoring before forwarding; preparation failure disables forwarding with an error. The legacy `NativeFnBackend.open` also starts the monitor before event emission and uses its Fn state. In the main emitter, these modifiers’ family and side bits are removed from aggregate flags before merging the monitored state and app-owned holds; Caps Lock and other state retain their existing handling. When the tap is disabled, its untrusted cache is cleared before re-enabling. Forwarding does not wait indefinitely for physical key input; the next side-key event rebuilds that side’s state. A physical modifier already held at startup or during a missed-event interval must be released and pressed again. Invalid ports and failed creation or re-enabling report errors; destruction removes and releases the run-loop source and tap. The monitor reads modifier metadata, not keyboard text. The log at 00:42:57/59 on 2026-09-22 observes one physical Fn press/release pair from source PID 0, not every keyboard-overlap case; see the [modifier-feedback excerpt](evidence/2026-09-22-modifier-feedback.log). The two post-fix physical trials and their limits are recorded below.

Input suspension, disconnect, loss of online status or permissions, system sleep, configuration replacement, and shutdown clear all momentary-layer activations, cancel unresolved gestures, pending keyboard groups, and any remaining repeat pulses or macro steps, and attempt to release owned keys. Cancellation never flushes a delayed single action into the newly focused application. Held push controls are quarantined until their physical release after a configuration change, preventing a held key from becoming a new action under the replacement map. A failed release remains pending for retry rather than being treated as successful. Sleep immediately gates input callbacks while the worker cancels gestures and closes the connection; waking reconnects only if the user had not manually disconnected. No pending pre-sleep action is replayed.

An app activation error or timeout stops the remaining macro. After a macro selects an app, subsequent key steps require that app to remain in the foreground; a focus change cancels the sequence rather than sending those keys into a different app. Cancellation invalidates pending activation work so late completions cannot resume a canceled macro. A target app may still finish launching after cancellation, but its remaining macro keys are not replayed.

Studio heartbeats default to disabled. They are enabled only when a successfully saved valid host map, a connected and online device, Input Monitoring and Accessibility permissions, and unsuspended input are all ready. An unsaved default draft, a local configuration-file error, or missing permissions leaves read-only vendor queries available without continuing to take over device input through heartbeats. Permission diagnostics are independent of map initialization and device online status. Outside demo mode, missing Input Monitoring or Accessibility permission replaces the main app window's content with the permission welcome page and authorization guidance, without opening a popup, another window, or a sheet, or entering the configuration workspace or settings interface. Both permissions becoming ready opens the workspace automatically; revocation returns to the welcome page, without stacking initialization errors and footer notices. Query waits also check suspension conditions. Normal online queries retain the last confirmed state until completion, avoiding cancellation of held actions every two seconds.

The idle-stop preference is stored locally and independently of `HostKeymap`, its drafts, and exported profiles. Its default is Never; supported timeouts are 1, 5, 10, 15, 30, and 60 minutes, applied immediately from the Vibe Key section in Settings. The worker measures only physical Vibe Key key and knob activity. While a push control is held, timeout is suppressed; release restarts the interval. Read-only status/battery queries, other computer input, and window visibility never refresh the activity deadline.

Reaching that deadline latches an idle pause, gates heartbeat and host forwarding, cancels gestures, layers, keyboard groups, and macros, and releases owned keys. Firmware mappings may resume on the device. Vendor reports do not clear the latch or trigger host actions while paused, preventing double output if standard HID has returned. Explicit Resume Keepalive from Settings or the menu bar, a real receiver reconnection, Mac wake, or a confirmed device offline-to-online transition clears the pause and starts a new interval, subject to the usual configuration and permission gates. The last confirmed online state is tracked across failed queries: an unknown-to-online result alone is not a reconnect and does not resume. These runtime rules do not establish physical device sleep or power savings.

An idle pause also stops the background online query every two seconds and battery query every 20 seconds, retaining receive callbacks and USB removal detection so background traffic does not interfere with firmware standby and sleep timers. Online status and battery values remain the last readings before the pause, not proof of current wakefulness. While paused, the service cannot automatically detect the device body going offline and online again; click **Resume Keepalive** after physically waking it. Explicit connection checks or refreshes still send requests, but a successful query alone does not clear the pause. Stopping keepalive does not change on-device standby or sleep durations or imply immediate sleep; actual timing and power savings require hardware verification.

The app independently reads `InputPermission.currentStatus()` once per second in the main run loop's common mode, without depending on window activation or completion of device jobs and without requesting authorization. Polled results are stored separately so older device snapshots cannot roll them back; only changes ask the service to recheck immediately and automatically switch the welcome page. Stopping or destroying the model cancels the timer; demo mode does not read real permissions. Input Monitoring first reads the CG listening preflight. Only when false does it create a temporary session-level, listen-only, keyboard-only capability probe, checking that it is valid and enabled before immediately releasing it without joining a run loop or reading events. A true preflight skips the probe. Either successful check means current keyboard-listening capability is `已就绪` (ready), not that the UI mirrors a separate Settings switch. HID and event-synthesis preflight remain diagnostic values. Accessibility reads `AXIsProcessTrusted()` unconditionally on every check, preventing any other preflight from short-circuiting the real AX state. `ListenProbe` diagnostics distinguish probe results from skipped checks.

Device-query waits continue to deliver physical events, so a readback cannot compress an entire Fn hold into two events after the query returns. Gesture deadlines are serviced by the worker; no window timer owns input behavior. Explicit device-map import, profile import, and host-action validation reject unknown action types and unsupported macOS usages instead of guessing input. Unsupported types in an ordinary device readback do not block default drafts or an existing host map. F21–F24 have no supported virtual-key mapping in this implementation.
